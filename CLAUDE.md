# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A local **climate-monitoring application** for the **testo Smart Connect API**, plus a curated AI-readable snapshot of that API's docs. It has two halves:

- **The app** — a Node/Express/SQLite backend that polls the testo Smart Connect cloud on a schedule and stores measurements, device status and alarms, plus a React (Babel-in-browser, no build step) dashboard that visualises them. Key locations:
  - `backend/` (14 modules) — `server.js` (Express REST API), `scheduler.js` (sync cycle), `event-reconcile.js` (the alarm-episode window functions, extracted from `scheduler.js` so the partition key lives in **one** place — `EPISODE_PARTITION`; it recomputes `active` and `end_ts` over **all** stored feed rows every cycle, **not** incrementally, which is what lets historical episodes settle by themselves — do not optimise that away), `testo-client.js` (async submit→poll→download client), `device-bridge.js` (pure mapping helpers), `db.js` (better-sqlite3 schema + settings), `listen-error.js` (turns any bind error into one clear log line + exit≠0 so the Windows task can restart; scheduler and update check start only in the `listen()` success callback), `log.js` (timestamped `info/warn/error` + `logThrottled` — every backend log line goes through it; the scheduler writes exactly one heartbeat line per sync cycle), `update-check.js` (looks in a drop folder for a newer release ZIP, reported via `GET /api/system/status`; the status also carries `dir`, `latestFile`, `checking` and, when the folder is unreadable, the reason as German plain text in `error` (`describeReadError`: computer-account read right, mapped drive letter instead of UNC, else code + message). Only one check runs at a time — triggers during a run collapse into exactly one re-run, because a dead UNC target holds a libuv thread until the SMB timeout and `dns.lookup` for the testo sync shares that pool. It doubles as a CLI, `node backend/update-check.js --check-update <dir> [--pick-file <file>]`, a **stable contract** with `deploy/windows/update.cmd`: exit 0 = newer version found, 10 = nothing newer, 2 = folder unreadable, 3 = bad invocation or own `VERSION` unreadable; code 1 stays free for crashes (Node exits 1 on an uncaught exception, which must never read as "no update"); with `--pick-file` the file gets exactly one ASCII line `<version> <file>`, no newline; the accepted switches are exported as `CLI_FLAGS`, and `backend/tests/deploy-contract.test.js` holds update.cmd's single call line against them). CSV export + backup subsystem: `export-service.js` (DB-bound orchestration, shared by manual export and backup), `csv-export.js` (pure table builders), `csv-format.js` (pure CSV dialect/formatting), `backup-runner.js` (monthly per-station ZIPs + a daily `VACUUM INTO` snapshot of the whole DB in `<backup_dir>/datenbank/`, newest 7 kept — the only restorable backup, restore steps in `deploy/windows/README.md`; `computePruneFloor` keeps retention from deleting anything not yet backed up), `zip-writer.js` (minimal PKZIP writer on Node's zlib). Tests in `backend/tests/` run via `npm test` (`node --test`).
  - `Smart Meter Dashboard/` (19 files) — `Klima Dashboard.html` (entry + the versioned script tags — 40 lines since the styles moved out), `dashboard.css` (all styles, loaded via a versioned `<link>`; it lives in this directory so the relative `url()` paths to `vendor/fonts/` keep working), `app.jsx` (grid shell), `header.jsx` (top bar), `tiles.jsx` (tile grid, drag/resize), `charts.jsx` (SVG chart primitives), `settings.jsx` (settings page), `ui-kit.jsx` (presentational building blocks shared by settings + export panel: `Card`, `Field`, `SectionHead`, `Toggle`, `SegmentedControl`, `StatusPill`, `StatusBadge`, `HealthCard`, `OpRow`, `KV`, `Spinner`, `NavIcon`, `formatBytes` — no hooks, so it deliberately carries no `= React` alias line), `export-panel.jsx` (CSV export dialog + backup settings), `summary-panel.jsx` (active-events detail panel), `data.js` (frontend data layer / `window.DASH_DATA`). Pure, DOM-free logic modules loaded as plain `<script>`s and unit-tested from Node (dual export: `window` + `module.exports`): `metrics-logic.js`, `summary-logic.js`, `status-logic.js`, `export-logic.js`, `partial-failure-logic.js`, `chart-logic.js` (`xPositions`, `buildPath`, `buildAreaPath` — the SVG path builders, extracted from `charts.jsx`; `xPositions` is the single x-coordinate producer both charts route through, so the one-sample `0/0` case is handled once; `gaugeScale` — the gauge scale from the metric's limits plus margin, else the data, rounded ends), `layout-logic.js` (`COLS`, `rectsOverlap`, `compactLayout`, `findFreeSlot` — the tile-grid maths, extracted from `tiles.jsx`) — their tests live in `Smart Meter Dashboard/tests/` and run as the second half of `npm test`. `tests/dashboard-load.test.js` is the safety net for the shared global scope: it parses every file the HTML loads (using the checked-in `vendor/babel.min.js`, no extra dependency) and fails on cross-file `const`/`let`/`class` collisions — the bare-hook-alias trap that renders a blank page — on identifiers used but never declared (a forgotten `<script>` tag), on syntax errors, on a stale `?v=` cache-buster, and on a file in the directory that no tag loads. `vendor/` holds the checked-in React/ReactDOM/Babel/Geist assets (see the no-external-assets rule below). Note the directory name contains spaces.
  - `scripts/` — **empty since 2026-09-17.** It held six one-off DB migration scripts plus `args.js`; all six had run at the only installation and no further installations are planned, so they were removed. `README.md` is now a historical note recording what each repaired and the commit they live on (`4dd2fa8`) — it exists so that someone later understands why old data rows look different from new ones. `VERSION` + the README badge + the `?v=` query in the HTML script tags all carry the SemVer version and must stay in sync; `backend/tests/version-sync.test.js` holds the badge, `package.json` and the `appVersion` line in `deploy/windows/README.md` against `VERSION`.
  - `deploy/windows/` — the Windows service scripts (`install.cmd`, `setup.ps1`/`setup.cmd`, `install-task.ps1`, `start.cmd`, `uninstall-task.ps1`) and the IT guide with the §9 acceptance (`README.md`); every `.ps1`/`.cmd` must be pure ASCII (CI guard). `update.cmd` (v0.18.0) is never run from the installation: the IT copies it once into the drop folder next to the release ZIPs. It rewrites a mapped drive letter to UNC, elevates via UAC (`cmd /k`, so an unreadable share stays on screen), refuses to run from an installation or bundle, lets the **installed** program pick the version via the CLI above, asks J/N, copies the ZIP into the hardened `C:\Apps\TestoSmartAbruf.update`, checks that `install.cmd`, `node.exe` and `VERSION` sit in the ZIP root and that `VERSION` matches the file name, then `call`s the **new** bundle's `install.cmd` (DB snapshot `klima-vor-update.db`, staging, switch, version check in `setup.ps1`, automatic rollback).
  - `.github/workflows/` — `test.yml` (`npm test` on every push/PR) and `windows-bundle.yml` (the Windows release bundle + E2E smoke, then an install test that runs the shipped scripts for real: 1/4 first install from the release ZIP via `install.cmd`, task running as NetworkService; 2/4 update notice under NetworkService — local drop folder with decoys (0-byte ZIP, `.part`), and a folder NetworkService may not read must report `error`; 3/4 `update.cmd` via mapped drive `Q:` on an SMB share — first the bootstrap refusal with an emptied `update-check.js`, then the real update to a 99.0.0 test ZIP, UNC rewrite, readable `klima-vor-update.db`; 4/4 rollback via UNC with a deliberately broken 99.1.0 — `.failed`, new PID, `klima-vor-update.fehlgeschlagen.db`. Test ZIPs are built outside the workspace, and the release upload names the exact ZIP. Runs only on `v*` tags or manual dispatch; kept separate so the heavy job does not run on every push).
- **The API docs snapshot** — `testo-smart-connect-api/` holds the curated upstream API documentation (endpoints, async pattern, auth, OData, schemas, limit values, Saveris 2 migration).

Run the app with `npm start` (serves on port 3000). Tests: `npm test`.

## Deployment target: the app must stay Windows-runnable

The application is deployed as a **login-independent background service on a corporate Windows 11 x64 machine** (Windows Task Scheduler, account `NT AUTHORITY\NetworkService`, BootTrigger). Shipped in v0.10.0. The dev machine is macOS, so Windows behaviour is confirmed by content review, the CI install test in `windows-bundle.yml` (install, update, rollback) and a manual acceptance pass on a Windows box (UAC, real share). Detailed design / plan / IT setup guide: [docs/superpowers/specs/2026-06-22-windows-service-design.md](docs/superpowers/specs/2026-06-22-windows-service-design.md), [docs/superpowers/plans/2026-06-22-windows-service.md](docs/superpowers/plans/2026-06-22-windows-service.md), [deploy/windows/README.md](deploy/windows/README.md) (the latter holds the §9 acceptance criteria).

**Any change to the app must keep these true** — they are easy to break from macOS, where the broken version still looks fine:

- **Paths:** always `path.join(__dirname, …)`; never hardcode `/`, Unix paths, or manual `'/'` concatenation. The DB path comes from `process.env.DB_PATH` (the service points it at `C:\ProgramData\TestoSmartAbruf\`) — never assume the code directory is writable (it may be read-only / under `C:\Program Files`).
- **Env loading:** dotenv is called with `{ path: path.join(__dirname, '../.env') }` (CWD-independent) because the service runs with a foreign working directory. Do not revert to bare `require('dotenv').config()`.
- **npm scripts:** no inline `VAR=value cmd` (breaks cmd.exe/PowerShell) — use `cross-env` (already a devDependency), as the `test` script does.
- **Native modules:** only add native deps that ship **win32-x64 prebuilds for Node 22/24/26** (the pinned `engines` / `.nvmrc=24`; Node 23/25 are excluded). Avoid deps that need a compiler — that breaks the corporate "nothing-surprising" / no-build-tools constraint. `better-sqlite3` is the only native module today.
- **"Nothing surprising" for corporate EDR:** no new bundled binaries, no surprising network calls at startup. The only outbound traffic is the testo-cloud sync — the dashboard's React, Babel and fonts ship locally under `Smart Meter Dashboard/vendor/`, so opening it needs no internet. Keep it that way: no CDN, and nothing heavyweight in `dependencies` (the server installs with `npm ci --omit=dev`, and the CI copies `node_modules` verbatim into the Windows bundle).
- **No external frontend assets:** React, ReactDOM, Babel and the Geist fonts are checked in under `Smart Meter Dashboard/vendor/` and served locally — the dashboard makes **zero** external requests when opened. Never reintroduce a CDN (`unpkg`, `fonts.googleapis.com`, `fonts.gstatic.com`): the customer's IT allowlist contains the testo host only, so a CDN reference silently yields a blank dashboard on the target machine. `deploy/windows/README.md` documents this in "Voraussetzungen" and the §9 offline probe.
- **SQLite WAL:** the DB must stay on a **local disk** — WAL breaks on UNC / network shares.
- **Schema changes are additive only:** the previous version must tolerate every new schema; `install.cmd` rolls back code only, never data. After a failed update the old version runs on the DB as the new one left it (restoring `klima-vor-update.db` is a manual step), and the CI rollback test cannot catch a violation. Same rule as a comment at the migration in `backend/db.js`.
- **Update path — IT constraints:** no internet and no GitHub API, the drop folder is the only channel; the service only *lists* the drop folder (allowlist `readdir`/`stat`/`lstat` over every `fs`/`fs.promises` function, test `IT-Vorgabe "nur Listing"` in `backend/tests/update-check.test.js`); the service starts no programs — no `backend/*.js` mentions `child_process` (test `IT-Vorgabe "startet keine Programme"`, same file), installing is the IT's `update.cmd`; no self-lock — the service only reports and always starts (user's decision 2026-09-18: a locked monitoring service is worse than an old version).
- **Server binding:** configure via `PORT` / `HOST` env; `HOST` defaults to localhost. LAN access is opt-in (a firewall rule), never the default.
- **On release / when the deployment story changes:** keep `VERSION`, the README badge, `package.json` version, and all `?v=` cache-busters in `Klima Dashboard.html` (every app script tag **and the `dashboard.css` stylesheet `<link>`** — currently 18 in total; the three `vendor/` tags deliberately carry none) in sync; update `deploy/windows/` and re-run the Windows acceptance.

## Editing safety rails

- Every `.md` file (except the inner index and `_assets/glossary.md`) carries YAML frontmatter with `source_url`, `snapshot_date`, and `source_chunks`. This frontmatter is load-bearing for re-snapshotting — preserve it on every edit. Mechanics are described in the inner index's "How this directory was built" section.
- [testo-smart-connect-api/_assets/glossary.md](testo-smart-connect-api/_assets/glossary.md) is the single source of truth for terminology (endpoint names, async status enum, header casing). A cross-consistency reviewer greps for violations — match its spellings exactly.
- **Do not invent** endpoint paths, status enum values, header names, or schema fields. If a fact is not in an existing snapshot file with a `source_chunks` reference, re-fetch from upstream rather than writing it from memory.

## Running the app

Start command: `npm start` (runs `node backend/server.js`), serves on `http://localhost:3000` (default `PORT=3000`, overridable via env). **Claude Code sessions: don't re-derive this** — `.claude/launch.json` already defines the server config `dashboard`; start the app via `preview_start` with that name.
